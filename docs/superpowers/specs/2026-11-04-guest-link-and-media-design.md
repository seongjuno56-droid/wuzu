# 하객 링크와 사진 저장 설계 (1-C + 1-D)

작성일: 2026-11-04 · 상태: 사용자 확인 대기

상위 설계: `docs/superpowers/specs/2026-10-27-server-and-admin-design.md`. 이 문서가 다른 부분은 이 문서를 따른다.

## 1. 왜 만드는가

wuzu 의 핵심 가치는 만든 초대장을 사람들에게 보내는 것이다. 지금은 초대장·사진·방명록·참석 응답이 전부 만든 사람의 폰 안에만 있어서 다른 사람이 볼 수 없다.

사용자가 말한 완성의 모습:

> 초대장이 완성되었다는 안내와 함께 링크를 공유한다. 카카오톡으로 보내면 썸네일과 링크가 잘 들어오고, 누르자마자 초대장이 잘 열린다.

1-C(서버 저장·웹 링크)와 1-D(사진 저장)는 원래 나뉘어 있었다. 사진이 폰에만 있으면 하객 화면에 사진이 안 나오고 썸네일도 만들 수 없어서, 사용자 승인으로 하나로 합쳤다(2026-11-04).

## 2. 목표 · 비목표 · 하면 안 되는 것

**목표**

1. 앱의 초대장이 서버에 저장되어, 다른 기기와 하객이 같은 내용을 본다.
2. 사진·GIF·동영상·BGM 이 R2 에 올라가 하객 화면에 나온다.
3. 활성화를 마치면 완료 안내와 **공유하기**가 나오고, 웹 링크가 공유된다.
4. 만든 사람이 링크 썸네일을 직접 올릴 수 있고, 카카오톡·문자에 제목과 그 썸네일이 나온다.
5. 링크를 누르면 앱 없이 카카오톡 안 브라우저에서 바로 열린다.
6. 방명록과 참석 응답이 서버에 저장되고, 만든 사람이 앱에서 본다.
7. 기간이 끝났거나 숨김 처리된 초대장은 내용 없이 안내 화면만 보인다.
8. 만든 사람이 초대장을 지우면 파일도 지워지고, 운영자가 어드민에서 초대장을 숨기거나 지울 수 있다.

**비목표 (이번에 안 함)**

- 레터·결제 서버화, 가입 지급 레터 (2단계). 레터는 mock 그대로 차감한다.
- 하객 신고, 공유·조회 기록, 어드민 방명록 화면, 어드민 초대장의 만료일 조정·통계 (3단계). 어드민 초대장 제어는 8장에서 이번에 한다.
- 안 쓰는 파일 정리 예약 작업, 어드민 저장소 화면 (4단계). 단 8장의 탈퇴 파일 삭제는 이번에 한다.
- 자체 도메인 구매·연결과 그 환경의 속도 재측정 (출시 준비, 사용자 결정 2026-11-04). 이번 확인은 `vercel.app`·`r2.dev` 로 하고, 이 주소로 보낸 링크는 시험용이라 나중에 끊겨도 된다.
- 링크를 앱으로 여는 유니버설 링크·앱 링크, 카카오 SDK 공유 (도메인·정식 빌드 이후).
- 기기 안 mock 초대장을 서버로 옮기는 일. 실제 사용자가 없어 버린다.

**하면 안 되는 것**

- 로그인 없이 남의 초대장·방명록·참석 응답을 고치거나, 참석자 이름·연락처를 볼 수 있는 것.
- 작성 중이거나 활성화 전인 초대장이 링크로 보이는 것.
- 링크가 보내진 뒤에 주소 형식이 바뀌어 끊기는 것.
- 결혼식 당일에 링크가 안 열리는 구조.
- R2 비밀 키가 앱·채팅·저장소에 들어가는 것.
- 원본 사진을 그대로 저장해 비용이 늘어나는 것.

## 3. 사용자 흐름

**만든 사람**: 작성 → 저장(이때 파일 업로드) → 최종저장 → 활성화 → **완료 안내 + 공유하기** → 휴대폰 공유 시트에서 카카오톡 선택 → `초대장 이름 + 웹 주소` 전송.

지금 활성화가 끝나면 나의 초대장으로 바로 넘어간다. 그 사이에 완료 안내를 넣는다. **작성 중이거나 활성화 전인 초대장에는 공유 주소를 주지 않는다**(사용자 결정). 주소는 첫 활성화 때 한 번 만들고, 그 뒤 수정·연장해도 바뀌지 않는다.

**하객**: 카카오톡에서 썸네일 카드를 본다 → 누른다 → 카카오톡 안 브라우저에서 초대장이 열린다 → 방명록·참석 응답을 쓴다. 로그인은 없다.

**링크 상태별 하객 화면**

| 초대장 상태 | 화면 |
|---|---|
| 활성화 중 | 초대장 |
| 활성화 전 또는 없는 주소 | "초대장을 찾을 수 없어요" |
| 기간 만료, 파일 정리됨 | "기간이 끝난 초대장이에요" (상위 설계 3장) |
| 숨김(banned) | 찾을 수 없음과 같은 화면 |
| 삭제됨 | 찾을 수 없음과 같은 화면 |

**회원 상태는 하객 화면에 영향을 주지 않는다.** 정지된 회원의 초대장도 계속 열린다(사용자 결정: 결혼식 당일에 링크가 끊기면 안 된다). 하객 읽기와 방명록·참석 응답 쓰기는 초대장 표만 보고 회원 표와 조인하지 않는다(사용자 결정). 문제 있는 초대장은 운영자가 초대장 단위로 숨긴다. 탈퇴 신청 중인 회원의 초대장도 기간까지 열리고, 탈퇴 확정 때 사라진다 (Claude 판단).

## 4. 만드는 방식

| 항목 | 결정 | 누가 |
|---|---|---|
| 하객 웹 호스팅 | Vercel. 어드민과 같은 팀 sjport 의 새 프로젝트 `wuzu-guest`. 어드민 때문에 Pro 를 어차피 내므로 추가 요금이 없다. 개발 중에는 Hobby, **실제 하객에게 링크가 나가기 전에 Pro 로 올린다** | 사용자 (2026-11-04) |
| 도메인 | 하객 링크용으로 새로 사되 **이번 작업에는 넣지 않는다**. 지금은 `*.vercel.app` | 사용자 |
| 어드민 호스팅 | Vercel 유지. 출시 전 Pro 필요 | 사용자 결정(비용) |
| 파일 저장 | Cloudflare R2. 이미 결정됨 | 사용자 |
| 주소 | `https://<도메인>/i/<slug>`. slug 는 추측 불가능한 난수 10자 이상, **첫 활성화 때 서버가 발급**. `invitations.slug` 는 지금 필수 칸이라 새 마이그레이션으로 비어 있을 수 있게 고친다 | 사용자 |
| 데이터 접근 | 앱은 Supabase. RLS 또는 security definer RPC. 하객은 익명 RPC 로만 | Claude 판단 |
| 업로드 시점 | 기기에 두다가 **저장을 누를 때** 바뀐 파일만 올린다. 고를 때마다 올리면 버려진 파일이 쌓인다 | Claude 판단 |

사용자가 만들 계정: Cloudflare(R2 전용). 키 입력은 사용자가 하고 단계별 안내를 `docs/setup/guest-link.md` 에 쓴다.

## 5. 데이터와 서버

**초대장**: `Invitation` 전체를 서버에 저장한다(`supabase/migrations/20261027000001_core.sql` 의 `invitations`). 본인만 읽고 쓴다. 번호·작성자·제작일·활성화 기간·제재·slug 는 서버가 정하며, 앱이 보낸 값은 무시한다. 지금 mock 의 `save` 규칙을 그대로 옮긴다: 활성화 중인 초대장은 일반 저장이 `PAID_EDIT_REQUIRED` 로 거부된다.

**ID 와 slug**: 앱 내부는 uuid, 공유 주소는 slug. 작성 중에는 slug 가 없다. 지금 앱은 `inv-…` 형식 ID 를 기기에서 만들므로, 서버가 주는 ID 로 바꾼다. 앱 안의 `/invite/[id]` 화면은 미리보기로 유지한다.

**활성화·연장·수정**: 레터는 mock 지갑에서 차감하고, 활성화 기간은 서버 함수로 저장한다. **2단계 전까지는 로그인한 회원이면 레터 없이 활성화할 수 있는 구멍이 서버에 남는다.** 그래서 2단계 전에는 앱을 정식 출시하지 않는다(사용자에게 안내함).

**하객 읽기**: 익명 RPC 하나가 slug 로 활성화 중인 초대장의 표시용 값만 돌려준다. 회원 표와 조인하지 않는다. 소유자 ID, 방명록 확인 시각 같은 내부 값은 빼고, 상태(정상/만료/없음)를 함께 준다.

**링크 썸네일**: 초대장에 썸네일 파일 값을 더한다. 7장 참고.

**방명록**: 비밀번호는 서버에서 해시. 목록은 비밀번호 해시와 숨긴 글을 뺀다. 작성·비밀번호 삭제는 익명 RPC, 작성자 삭제는 로그인 본인 확인. 활성화 중인 초대장에만 쓸 수 있다.

**참석 응답**: 목록은 초대장 작성자만 본다. 하객은 제출 때 받은 응답 ID 와 비밀 토큰으로 자기 응답만 다시 읽고 고친다. 응답 ID 만으로는 못 읽게 한다(지금 mock 은 기기에 ID 만 저장). 마감 검사는 서버에서 한다.

**작성 제한**: 익명 쓰기는 입력 길이를 서버에서 검사하고 요청 수를 제한한다. 제한 방법은 구현자 재량이되, 방명록 도배로 비용이나 저장량이 늘지 않아야 한다.

**알림**: 지금 방명록·참석 응답 때 만든 사람에게 가는 mock 알림은 기기 안에서만 돈다. 하객은 다른 기기라 이 알림이 만든 사람에게 가지 않는다. 푸시는 4단계이므로, 이번에는 앱을 열 때 서버 목록으로 새 글을 표시하는 정도로 둔다.

## 6. 파일 저장

상위 설계 5장을 따른다.

- **사진**: 본 이미지 긴 변 1080px, 썸네일 긴 변 400px 두 벌을 WebP 로 기기에서 변환. 장당 100~200KB 목표. Expo SDK 58 에서 WebP 저장이 안 되는 플랫폼이 있으면 그 플랫폼만 JPEG 로 대체한다.
- **상한 축소**: GIF 장당 5MB, 동영상 15초·20MB (지금 10MB, 30MB). 넘으면 올리기 전에 안내.
- **BGM**: 지금 규칙(`checkAudioFile`) 그대로 올린다.
- **링크 썸네일**: 카카오톡 미리보기는 JPG·PNG 만 읽는다는 답변이 있어 WebP 를 쓰지 않는다. 800×400 JPEG 로 저장한다. 7장 참고.
- **업로드**: 기기가 Supabase Edge Function 에 서명 주소를 요청 → R2 로 직접 PUT. 함수는 로그인, 초대장 소유, 파일 종류, 크기 상한을 검사한다. R2 키는 Edge Function 비밀값으로만 둔다.
- **기록**: `media_files` 표(R2 키, 초대장, 종류, 바이트, 쓰임 여부)를 만든다.
- **저장 과정**: 초대장 JSON 의 기기 주소를 R2 공개 주소로 바꿔 저장한다. 파일 하나라도 실패하면 저장을 멈추고 다시 시도할 수 있게 안내한다. 이미 올린 파일은 다시 올리지 않는다. 대상은 `content`·`design` 안의 모든 파일 주소로, 캔버스의 사진·GIF·동영상과 BGM 을 포함한다.
- **R2 공개 주소**: `r2.dev` 는 개발 전용이므로 출시 때는 자체 도메인의 하위 주소를 쓴다. 저장 값이 도메인에 묶이지 않게 **키만 저장하거나 주소 변환이 가능하게** 만든다.
- **파일 정리**: 사진 교체로 안 쓰게 된 파일은 `media_files` 에 표시만 하고 실제 삭제는 4단계. **만든 사람이나 운영자가 초대장을 지우면 그 파일은 8장의 삭제 대기열로 바로 지운다.** 작성 중인 초대장의 파일은 추측 불가능한 키로 저장하되 공유 주소는 없다.

## 7. 하객 웹과 미리보기

- **미리보기 태그**: `/i/<slug>` 요청에 Vercel Function 이 초대장 제목·설명·썸네일을 Open Graph 태그로 넣어 준다. 미리보기를 읽는 카카오톡 봇은 자바스크립트를 실행하지 않으므로 서버에서 만들어야 한다.
- **링크 썸네일 등록 (사용자 결정)**: 만든 사람이 이미지를 직접 올리는 입력을 정보 입력 화면에 둔다(위치는 구현자 재량, 선택 항목). **입력 칸 바로 아래에 크기 안내를 보여 준다**: "권장 800×400px (가로:세로 2:1), JPG·PNG". 다른 비율은 올릴 때 가운데 기준으로 2:1 로 잘라 미리 보여 준다 (Claude 판단).
- **썸네일을 안 올렸을 때**: 대표 사진 → 인사말 사진 → 갤러리 첫 장 → wuzu 기본 이미지 순서 (Claude 판단). 대체 이미지도 같은 크기의 JPEG 가 있어야 하므로, 저장 때 만들어 둔다.
- **카카오톡 캐시**: 같은 주소의 이미지를 카카오톡이 오래 기억할 수 있으니, 썸네일을 바꾸면 파일 주소도 바꾼다. 활성화 뒤 썸네일 변경은 다른 내용과 같은 수정 규칙(레터)을 따른다 (Claude 판단).
- **Function 장애**: Function 이나 Supabase 호출이 실패해도 초대장 화면은 열려야 한다. 미리보기 태그만 기본값으로 나가고 하객 화면은 그대로 뜬다. 결혼식 당일에 링크가 안 열리면 안 되므로, Pro 에서 사용량 때문에 멈추는 설정(자동 일시 중지)을 켜지 않는다.
- **웹 범위**: 공개 웹에는 `/i/<slug>` 하객 화면과 `/privacy` 개인정보 처리방침만 둔다. 로그인·작성·지갑 등 앱 화면이 공개 도메인에 노출되지 않아야 한다.
- **속도**: 지금 웹 번들은 앱 전체가 들어 있어 JS 3.5MB(압축 전), 그 밖에 자산이 약 20MB 다. 구현 전에 하객 화면이 실제로 받는 양을 측정하고, 필요하면 하객 전용으로 줄인다. 목표: 4G 휴대폰에서 3초 안에 표지가 보인다 (Claude 판단, 측정 후 조정).
- **브라우저**: 카카오톡 안 브라우저(아이폰·안드로이드)와 사파리·크롬에서 동작해야 한다. 카카오톡 안 브라우저의 자동재생 제한, 지도·주소 복사, 달력 추가 동작을 확인한다.
- **환경 변수**: 공개 웹은 publishable 키만 쓴다.

## 8. 탈퇴와 개인정보

- `finalize_withdrawals` 가 초대장을 지울 때 R2 파일도 지운다. DB 함수는 R2 에 직접 접근할 수 없으므로 삭제할 키를 `media_files` 등에 남기고, 예약 Edge Function 이 지운다. "사진 30일 뒤 삭제" 문구가 이미 공개되어 있어 이 단계에서 반드시 지킨다.
- **만든 사람 삭제**: 초대장·방명록·참석 응답을 지우고 파일을 삭제 대기열에 넣는다. 복구할 수 없다.
- **어드민 초대장 제어 (사용자 결정)**: 어드민 `초대장` 메뉴를 만든다. 번호·이름·회원 아이디로 찾기, 상태 보기, **숨김/해제, 삭제(파일 포함)**. 숨김은 파일을 두어 해제할 수 있고, 삭제는 되돌릴 수 없어 확인 창과 작업 기록을 거친다. 어드민은 지금처럼 서버에서 DB 직접 연결을 쓴다.
- **하객 정보 고지 (사용자 결정, 추천대로)**: 방명록·참석 응답 입력 폼 아래에 수집 항목·목적·보유 기간을 담은 짧은 안내와 처리방침 링크를 둔다. 체크박스를 넣지는 않는다. 기본 정보 외에 입력을 늘리지 않는다.
- **하객 정보 보유 기간 (사용자 결정, 추천대로)**: 방명록과 참석 응답은 초대장 만료 후 30일에 지운다. pg_cron 으로 매일 실행한다. 연장으로 만료일이 늦춰지면 그만큼 남는다. 그때 만든 사람에게 내려받기를 주는 일은 이번에 하지 않는다.
- **처리방침**: 공개 웹 `/privacy` 에 앱과 같은 내용을 둔다. 하객 입력 정보, Cloudflare 저장, 국외 이전·처리 위탁 항목을 추가한다.
- **법적 확인**: 사용자 요청으로 다른 서비스 사례를 찾았으나 방침 원문에서 하객 정보를 다룬 예를 찾지 못했다. 처리방침 공개는 개인정보 보호법 제30조의 의무로 보이고, 체크박스 없이 안내로 충분한지는 불확실하다. **출시 전에 전문가 확인을 받는다.**
- 초대장 만료 후 파일 삭제는 4단계. 그때까지 방명록·응답만 먼저 지워진다.

## 9. 앱 쪽 변경

## 확인 결과

2026-11-04 Task 1 기록. 실기기 시험 없이 문서로 확인한 내용이다.

- **WebP 저장**: `SaveFormat.WEBP` 는 Expo SDK 58 `expo-image-manipulator` 문서에 있지만 플랫폼별 동작은 미확인이다. 코드에서 WebP 저장이 실패하면 JPEG 로 대체하고, Task 11 에서 아이폰으로 확인한다.
- **BGM wav·m4a 업로드**: Task 11 에서 안드로이드로 확인한다. Expo 58 은 전역 `fetch` 를 `expo/fetch` 로 바꾸고, 여기서는 직접 준 헤더가 Blob 형식을 이긴다. 안드로이드에서 Blob 형식이 헤더를 덮어쓰는 것은 RN 기본 XHR fetch 의 동작이다. 앱이 PUT 직전에 Blob 형식을 서명한 형식에 맞추는 처리는 그래서 방어용이다. 기기가 알리는 형식(`audio/x-wav`, `audio/x-m4a` 등)이 서명한 형식과 다르기 쉬운 두 종류로 실제 업로드가 되는지 본다.
- **파일 읽기와 메모리**: Task 11 에서 `file:`·`content:` 주소를 이 `fetch` 로 읽어 올리는지, 20MB 동영상에서 메모리가 버티는지 본다. 코드로 본 내용(실행 확인 아님): `expo/fetch` 의 안드로이드 구현은 `file://` 만 따로 처리하고 `content://` 는 처리하지 않아 읽기가 실패할 수 있다. 응답 `blob()` 은 네이티브 저장소를 거쳐 base64 로 복사하고, 요청 본문은 전체를 메모리의 바이트 배열로 바꾼다. 안 되면 `expo-file-system` 으로 읽는 방식으로 바꾼다.
- **속도**: JS·글꼴·이미지 크기 (Task 9 측정 후 기록), LTE 표지 표시 시간 (Task 9 측정 후 기록).
- **카카오톡 카드**: Task 9·11 에서 실제로 확인한다.
- **Function 한도**: 하객 웹 호스팅이 Vercel 로 바뀌어 Cloudflare Function 한도 시험은 필요 없다. Vercel 문서 기준으로 Hobby 는 사용량을 넘으면 대개 30일을 기다려야 하고 비상업 용도로만 쓸 수 있으므로, 실제 하객에게 링크가 나가기 전에 Pro 로 올린다. Pro 에서는 Spend Management 의 Pause all production deployments 를 켜지 않는다. 실제 한도 도달 시험은 하지 않았다.
- **`wuzu-guest` 첫 배포**: 저장소 맨 위에 `build` 스크립트·`public`·`vercel.json` 이 없다. Vercel 문서상 Framework Preset 이 Other 이면 맨 위 폴더를 출력으로 삼으므로, 그대로 배포하면 저장소 파일이 공개될 수 있다. 그래서 설정 안내에서 Build Command 를 `exit 1` 로 덮어써 Task 9 전까지 빌드를 실패시킨다. Task 9 의 `vercel.json` 에는 `buildCommand` 와 `outputDirectory` 가 반드시 있어야 한다.
